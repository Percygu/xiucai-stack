# 视觉标准（封面 + 内页）

所有标准都已固化进 `assets/cover.html` 与 `assets/inner.html` 的 CSS；本文件解释**为什么这样定**，便于改时不破坏调性。参考成品见 `examples/llm-gateway/output/`。

## 0. 画布

- 一律 **1080 × 1440 px（竖屏 3:4）**。这是小红书信息流展示面积最大、点击率最高的比例，封面和内页统一用，保证一组图不被裁切。
- 渲染用本机无头 Chrome `--window-size=1080,1440 --force-device-scale-factor=1`，所见即所得。

## 1. 封面卡（两种风格随机）

小红书知识类爆款封面的精髓是「刻意做的高级的随意感」，不是企业级精致设计。每篇在两种风格里**随机选一种**（避免账号每篇一个样、太机械），背景一律**淡色**。

通用规则：
- **背景淡色系**（低饱和高明度）。背景池 8 色：`cream 米白 / blue 淡蓝 / pink 淡粉 / purple 淡紫 / green 淡绿 / yellow 淡黄 / mint 薄荷 / sky 天蓝`。每篇随机一个。
- **超大粗黑标题**占画面主体，保留文章原标题（仅去序号）。企业、轮次和真题出处须有原文依据或用户明确提供的真实背景，不能随机虚构；无依据时用“大模型面试题”等中性前缀。
- 发布页文字标题另按 `copywriting.md` 的“面试官：+ 精简题”处理，≤20 字；不要把封面长标题规则误用于文字标题字段。
- **关键词高亮**：给标题里 1–3 个关键词套高亮块（荧光黄/绿/橙）。
- **断句避免孤字**：高亮块要包住完整词，别让单个字单独成行被高亮（标题文案要按显示宽度手动断行）。
- **不额外加“模拟”**：封面大标题、角标、副标题和底部标签都不要擅自添加“模拟面试”等字样；用户已明确不采用这种处理。memo 的普通标签用“附参考回答”等原有文案。

### 封面铁律：只放标题文字 + 右上角引流（重要）
封面越干净越高级，**只允许两样东西**：
1. **居中的超大粗黑标题**（含 1–3 个关键词高亮）。
2. **右上角一处引流 handle `@IT杨秀才`**（社交账号 handle，**不是**网站名"秀才的进阶之路"——网站名只用在内页文档导航做站内引流）。`cover.json` 里 `brand` 填 `IT杨秀才`。

明确**不要**的东西（踩过的坑）：
- **不放任何表情/emoji 图标**。早期版本在角落塞一个 emoji（如 🚪），既和标题割裂、又显廉价、读者也看不懂为什么放它——一律去掉。`cover.json` 里 `emoji` 字段保留也不会渲染，可忽略。
- **不放副标题 / 卖点 / 左下角品牌**等"二次引流"，一处水印足够。
- memo 风格底部那个黑色药丸标签（如"附参考答案"）是 memo 的版式元素、可保留；按文章类型变（有答案→"附参考答案"，纯讲解→"建议收藏"，项目实战→"附完整方案"）。macaron 风格不放标签。

### 封面排版：垂直居中 + 字号双向自适应（重要）
- **标题整体垂直居中**：短标题不要堆在顶部、留大片空白，要在版面中央。`cover.html` 用 flex 居中已固化。
- **字号双向自适应**（`fitTitle`）：不是只在长标题时缩小，**短标题要放大填满版面**。逻辑是从基准字号先往上加（字少→放大到接近上限），超界再回退缩小（字多→缩到容纳全文）。这样无论原标题长短，封面观感都饱满。改模板时别退回"只缩不放"的旧逻辑。

### 风格 A：备忘录风（memo）
仿苹果备忘录：淡色横线纸 + 顶部黄色「‹ 备忘录」状态条 + 右上角 `@博主名`。标题深灰 `#33332f` 基准 104px/800（自适应）、垂直居中，关键词黄色高亮 `#ffe14d`。底部右侧黑色药丸标签（如「附参考答案」）。适合硬核面试题。

### 风格 B：马卡龙大字报风（macaron）
淡色纯底 + 超大黑标题基准 112px/900（自适应）、垂直居中 + **撞色高亮块**（绿 `#bdf0c4`/黄 `#ffe14d`/橙 `#ffd0a6`）+ 大引号装饰。**只有右上角一处 `@博主名` 水印，无 emoji、无副标题、无标签**。更跳、更抓眼球。

封面文案放在 `data/cover.json`（模型按文章生成钩子标题与高亮），风格与背景由 `render.mjs` 随机或显式指定。

## 2. 原文引流卡（只保留 1 张 · Claude 原版文档页）

目标：用 `.claude` 原版文档页证明内容来自完整文章、有上下文、有题库体系。**这张只作为第 1 张内页，不要把整篇文章都分页成文档卡发布。**

版式 1:1 还原 golangstar.cn 文档页。三栏：

### 顶部品牌导航（高 78px）
- 左：品牌 logo 图（`web_logo2.png`，34px 圆角）+「秀才的进阶之路」21px/800。
- 右：栏目链接 **18.5px**，带原站 emoji 图标（🔥/🤖），当前栏目「🔥后端/AI面试题」红色 `#e8453c`/700。
- **去掉「关于作者」「求职训练营」**——一是腾出宽度让导航字号能放大到 18.5px（1080 宽下 5 个栏目是上限，再多会截断），二是小红书不做站外引流不需要这些入口。
- 导航文字必须从当前项目 `src/.vuepress/navbar.ts` 或线上 DOM 原样抽取，禁止缩写或改写。固定顺序是：`Go语言进阶之路`、`🔥后端/AI面试题`、`🤖Go Agent实战指南`、`🔥Vibe Coding实战指南`、`🔥Agent项目`。

### 左侧完整题库目录（宽 322px，底 `#f7f8fa`）
- 展示**所有分类组**（Go/Mysql/Redis/消息队列/分布式/大模型面试题/后端场景题…），不是只列当前几十题——分类越全越显内容厚、越吸引人。
- 当前分类（大模型面试题）展开列出该组全部题目（如 40 题），其余分类折叠成标题（前缀 ▸）。
- 分组标题 20px/700，题目项 19px，当前篇高亮：蓝底 `#e9f1ff` + 蓝字 `#2f6fed`/700。

### 正文（白底，padding 32×40）
| 元素 | 字号 | 说明 |
|---|---|---|
| H1 文章标题 | 40px / 800 | 仅第 1 张卡顶部 |
| meta 行 | 17.5px | 作者 · 日期 · 阅读时长 · 标签药丸 |
| 正文 p | **22px** / 行高 1.9 | 两端对齐，这是读者主要阅读区，必须够大 |
| H2 一级小标题 | **35px** / 800 | 左侧 8px 蓝色竖条 `#2f6fed` |
| H3 二级小标题 | **29px** / 800 | 蓝色 `#2f6fed` |
| strong 关键词 | 继承 | 荧光黄下划线高亮 `#ffe88a` |
| code 行内代码 | 19px | 橙色药丸 `#e8590c` + 浅灰底 |
| figure 配图 | 满宽 | 圆角 + 细边 + 轻阴影，`max-height:600px` |

### 渲染方式
使用 `.claude` 原版 `inner.html` 读取 `data/content.html` 和 `data/meta.json`，但只导出 `?only=0`：
- 输出为 `01-origin-doc.png`。
- 只保留这一张原文页，后续全部改为小红书讲解卡。
- 不要直接截浏览器网页，不要把原文页全量分页输出。

> 字号是反复调过的定稿基线（正文 22 / H2 35 / H3 29 / 导航 18.5 / 目录 19）。要再调大，注意：① 正文变大→分页数增加；② 导航 >18.5px 在 1080 宽下会截断，只能靠减栏目或缩品牌来换空间。

## 3. 小红书图解讲解卡（必须高质量）

原文页之后的卡片必须重新设计成小红书讲解卡，用来把抽象概念讲得更像小红书。**这些卡片是主体，不是可有可无的补充。**

### 数量与顺序
- 数量由原文的实际内容和手机端可读性决定，不设凑数的最低页数。不能靠新增知识凑页，也不要为了固定张数缩字或挤三栏。
- 顺序严格根据 `source-narrative.md` 的原文论证计划，不能套固定“概念→选型→追问”链。
- 原文有参考回答才保留在最后阶段；没有时用原文结论收束，不凭空补答案或追问。

### 必须图文并构
讲解卡不能是纯文字点列。每张卡至少包含一种视觉结构：
- **流程图**：步骤、闭环、状态流转、Agent 执行链路。
- **树 / 图结构**：ToT、GoT、多分支搜索、节点聚合。
- **对比矩阵**：方案差异、优缺点、适用场景。
- **架构图**：模块、输入输出、数据流、工具调用。
- **代码 / Prompt 结构图**：字段、格式、约束、解析逻辑。
- **决策表**：什么场景选什么方案。

这里的“视觉结构”指信息关系本身被画出来。以下情况**不算视觉主图**：

- 两栏/三栏圆角框里各放一段文字。
- 一组上下排列的 bullet 或标题卡。
- 只换颜色、描边、背景或圆角的同一套框架。
- 中间摆几个装饰圆圈和箭头，但关键解释仍全部依赖下方文字。

### 版式多样性硬门槛

- 写 HTML 前先完成 `data/visual-plan.json`，格式见 `quality-gates.md`。
- 8–15 张讲解卡至少使用 5 种真正不同的结构；同一 `visualType` 不超过总数的 35%，相邻两张不得复用同一骨架。
- 至少 60% 的页面必须是丰富视觉页：主信息由流程、关系、层级、路径、选择或对照直接表达。
- `grid2/grid3/list/answer` 可以作为解释区或最后的回答页，但它们只是文字容器，不得被当成整套卡片的主要版式。
- 把整套 360×480 缩略图并排查看；如果第一眼像同一个「标题 + 几个框 + 总结条」反复复制，直接判失败。

### 信息密度
- 一张讲解卡只能讲一个核心问题，但必须讲透：标题给结论，图形承载结构，旁注解释关键差异。
- **禁止 PPT 摆图页**：不能只把几个圆圈/箭头/流程节点放在画面中间，旁边没有解释。用户看到每张图后必须立刻知道「这页在讲什么、为什么重要、面试怎么说」。
- 不要一页只放 3–4 个空泛短句。每个信息块都要有具体名词、场景、边界、误区或面试表达。
- 每张讲解卡必须让读者看清：
  1. **结论型大标题**：直接告诉用户这一页要记住什么。
  2. **视觉主图**：流程、树、图、矩阵、架构、代码/Prompt 结构之一。
  3. **必要解释**：解释对象、动作、结果和图中关系，不固定解释块数量，不为凑三条添加事实。
  4. **前后衔接**：以具体问题、因果或共同目标连接内容，不渲染“本页结论”“上一页”“下一页”等策划标签和页面导读；结论直接写，需要过渡时可用“接下来……”。原文并列方案不能硬画成执行先后。
- 画面密度服从讲清内容，不为填空白新增案例或误区。内容少时放大核心图解或合并相邻同节页面。
- 参考回答卡可以是段落，但必须放在最后，且不能替代发布正文。

### 手机端字号硬门槛（不可退让）
以下仅适用于小红书图解讲解卡；`01-origin-doc.png` 仍按上面的 Claude 原文页字号基线渲染。

在 1080×1440 画布上：
- 结论型大标题：**56–64px**。
- 副标题/导语：**28–32px**。
- 模块小标题：**34–38px**。
- 核心正文、解释句、表格单元格：优先 **30–32px**，任何情况下不得低于 **28px**。
- 辅助说明、节点副文、脚注式解释：优先 **26–28px**，绝对不得低于 **24px**。
- tag、chip、水印等短标签：**24–28px**；水印可以取 24px，但不能用更小字号藏信息。

排版约束：
- 内容放不下时必须拆卡；**禁止缩字号、压行高或裁掉文字来维持卡片数量**。
- 三栏及以上布局只适合短标签或极短结论。栏内出现 1 句以上连续解释文字时，优先改成纵向三行、两栏大块，或拆成两页。
- 四栏及以上不得承载正文句子。表格必须保证单元格正文 ≥28px，否则拆成多张“场景 → 方案 → 原因”卡。
- 所谓“完整显示”不等于“可阅读”；文字即使没有裁切，只要手机缩略图上需要放大才能看清，也视为失败。

渲染验收：
1. 用浏览器逐张读取所有可见文字的 computed font-size，核对上述门槛。
2. 将 1080×1440 成图等比缩到约 360×480，正文应无需放大即可辨认。
3. 检查无重叠、截断、遮挡、孤字和英文强制断词；图、表、注释都必须完整。
4. 任一张失败就拆页或重排，并重新检查整套；不能带着“仅技术上未溢出”的卡片交付。
5. 运行 `scripts/validate-job.mjs`，确认视觉策划、官网导航、图片顺序和尺寸全部通过；自动检查通过后仍要做整套缩略图肉眼验收。

### 纵向比例（必须肉眼检查）
讲解卡的竖向节奏要稳定，不能出现「标题和正文贴得很近，但正文下方到水印又空一大片」：
- 讲解卡按标题、主体、结论/承接和水印安排流式节奏；不强制每页同一黑框总结。统一的章节导航有助于连读，但不能代替实际过渡解释。
- 顶部 tag + 标题区控制在画面上方约 22%–28%，标题下方到说明/正文之间至少留 22–34px 呼吸空间。
- 说明文字到主体内容之间至少留 30px，不能标题、说明、正文三段挤成一坨。
- 主体内容区（主图 + 解释块 + 总结条）应从约 390–440px 开始，向下延伸到约 1240–1300px。
- **不要用绝对定位把底部总结条硬贴到水印上方**。这会把空白从底部转移到正文和总结条之间。总结条必须跟随正文主体自然排版。
- 底部总结条与上一块正文/图解之间的距离控制在 44–60px，让黑框和正文有明确分隔；与 `@IT杨秀才` 之间控制在 16–28px。不要让黑框和右下角引流信息之间出现大面积空白。
- 某页内容高度不足时增大有信息量的主图或合并页面；禁止为填版面添加原文没有的面试表达、误区或场景。
- 更准确地说：**不能移动黑框来填空，要让上方主体本身变高**。文字页增大段落卡的最小高度/行高；图解页增大主图或解释卡高度；矩阵页增加行高或补列信息。
- 渲染后抽查每张讲解卡：标题区、正文区、落款区三者比例要协调；正文区不得像一个贴在上半屏的 PPT 截图。

### 美观要求
- 使用 HTML/CSS/SVG 代码渲染，不用 AI 生图写中文，避免模糊和乱码。
- 颜色克制但要有层次：同一张卡最多 3 个强调色，避免淡黄底再大片黄高亮、蓝底配蓝高亮这类同色撞车。
- **每篇文章必须随机一套内页主题色池**，不能所有文章都用同一个浅底 + 同一个深色总结条 + 同一组蓝绿红描边。主题色池应和封面背景绑定，做到一篇统一、篇与篇不同。
- 推荐主题池：
  - `sky`：淡蓝/米白背景 + 深海军蓝总结条 + 蓝/青/珊瑚强调。
  - `sage`：淡绿/米白背景 + 深墨绿总结条 + 绿/蓝/珊瑚强调。
  - `lilac`：淡紫/米白背景 + 深梅紫总结条 + 紫/玫红/青绿强调。
  - `peach`：淡粉橙/米白背景 + 深咖灰总结条 + 橙/蓝/绿强调。
  - `mint`：薄荷/淡蓝背景 + 深青灰总结条 + 青绿/靛蓝/暖橙强调。
- 总结条不必永远纯黑，可以是低饱和深色（深海军蓝、深墨绿、深梅紫、深咖灰、深青灰），但必须保证白字对比度足够。
- 撞色避让：背景主色、关键词高亮、描边强调色不能同属一个 hue 家族。比如淡黄背景不要用大面积黄高亮，淡蓝背景不要让主描边和高亮都偏蓝，淡绿背景不要用大片绿色高亮。
- 渲染脚本要支持 `theme=random|sky|sage|lilac|peach|mint`，并把同一个 theme 传给本篇所有讲解卡；不要每张卡单独随机，避免一组图风格散。
- 底部黑色总结条不能压住水印，也不能遮挡主图；空间不够就删总结条。
- 每张卡必须肉眼检查：文字不重叠、不截断、不空洞、不像 PPT bullet 摘要。
