Cursor 最适合已经习惯 VS Code 的人上手 AI 编程。它保留了编辑器、文件树、终端、扩展和快捷键这些熟悉的工作方式，同时把 AI 补全、代码问答、跨文件修改、终端执行和 diff 审查放进同一个开发环境里。你不需要先学一套全新的操作系统，真正要适应的是一套新的协作节奏。

这篇只解决入门第一关：怎么安装并迁移 VS Code，怎么理解 Cursor 的几个核心入口，怎样用它读懂一个项目、做一个小改动、审查 diff、跑验证。重点不是把所有高级功能讲完，而是让你形成一个稳定的第一天工作流。

1. Cursor定位

Cursor 是基于 VS Code 生态改造的 AI 代码编辑器。它不是一个单独的聊天窗口，也不是 VS Code 上的普通插件，而是把 AI 作为编辑器的一等能力来设计。你可以一边写代码一边用 Tab 接受补全，也可以在侧边栏唤起 Agent 让它读项目、改文件、跑命令，还可以通过 Plan Mode 先让它给方案再执行。

这个定位很重要。很多新手装完 Cursor 后，只会打开聊天框问问题，于是把它用成了普通 AI 问答工具。Cursor 真正的优势在于它和项目文件、编辑区、终端、版本差异紧密连在一起。你给它一个任务，它不只是回答你，还能在当前项目里找文件、理解代码、提出改动、生成 diff，并让你审查。

2. 安装登录

Cursor 官方 Quickstart 的第一步很直接：下载安装、打开应用、登录账号，然后选择一个项目文件夹开始。macOS 需要 Monterey 12 及以上，Windows 需要 10 及以上，Linux 推荐使用 apt 或 yum 包安装，也可以使用 AppImage。对大多数新手来说，直接去 cursor.com 下载对应系统安装包即可。

第一次使用时，先不要打开一个很大的生产项目。更稳的选择是准备一个小项目，或者复制一份练习项目。这样你可以放心让 Agent 改代码、看 diff、跑命令，即使改错了也容易恢复。AI 编程工具的第一天，目标不是一口气完成大需求，而是熟悉它的工作节奏和安全边界。

登录完成后，先进入 Cursor 设置确认账号状态。后续模型、用量、隐私、规则、MCP、团队设置都会从设置入口管理。入门阶段只要确认能正常登录、能打开项目、能唤起 Agent，就已经具备继续练习的条件。

安装完成后，不要急着直接把生产仓库交给 Cursor。先做四个检查。第一，确认左下角账号已经登录，模型选择器能正常展开。第二，打开一个本地练习项目，确认文件树、编辑器、终端都能正常显示。第三，随便打开一个文本文件，输入几行内容，观察 Cursor Tab 是否会给灰色补全建议。第四，在 Agent 输入框里发一个只读请求，确认它能读取当前项目但不会直接改文件。

如果你在公司电脑或正式项目上使用 Cursor，还要提前看一眼隐私和团队设置。个人练习可以直接使用默认配置；公司代码则要确认团队是否允许使用云端模型、是否开启隐私模式、是否限制某些目录上传上下文。AI 编程工具不是普通编辑器，它会读取项目上下文，越早把边界弄清楚，后面越少踩权限和合规问题。

3. VS Code迁移

Cursor 对 VS Code 用户很友好。官方迁移说明里明确提供一键导入能力，可以把 VS Code 的扩展、主题、设置和快捷键带过来。不同版本的入口会略有变化，常见路径是在首次启动向导或账号设置里执行 VS Code Import；迁移完成后，可以在 Cursor 的 VS Code Settings 页面检查主题、字体、快捷键和扩展相关配置是否已经继承。

这里有一个现实细节要知道：Cursor 使用 Open VSX 扩展注册表，不是直接使用 VS Code Marketplace。大多数常见扩展都能用，但不是所有 VS Code 扩展都一定完全可用。迁移后如果发现某个扩展没出现，先去扩展面板搜索替代项，不要急着怀疑 Cursor 本身出问题。

迁移完成后，建议先检查三件事。第一，主题和字体是否符合你的习惯；第二，常用快捷键是否仍然有效；第三，项目里依赖的扩展是否正常。确认这些基础环境没问题，再开始体验 AI 功能。否则你会把编辑器配置问题误以为是 AI 功能问题。

更稳的检查方式是用一个真实项目跑一遍常用动作。先打开命令面板，确认你在 VS Code 里常用的格式化、重命名、跳转定义、全局搜索仍然可用；再打开扩展面板，检查语言服务、Lint、格式化器、Git 插件是否正常加载；最后打开终端，运行项目原有命令，比如 npm test、pnpm lint、go test ./...。这些命令不一定都存在，关键是用项目自己的验证方式确认编辑器环境没有断。

如果迁移后发现快捷键冲突，先不要一次性重改全部快捷键。优先处理三类高频动作：搜索文件、全局搜索、打开终端。AI 功能再强，也绕不开这些基础编辑动作。小白最容易忽略的是终端工作目录，Cursor 打开的项目路径必须和你准备操作的仓库一致，否则 Agent 后面运行命令时会在错误目录里执行。

4. Tab补全

Cursor Tab 是最高频、也最容易被低估的能力。普通补全通常只补当前变量名或当前一行，Cursor Tab 更像是在预测下一步编辑。你改了一个函数签名，它可能提示你同步更新调用处；你写了一个列表结构，它可能继续补出下一项；你修改了文案风格，它可能在相邻文案里保持一致。

使用方式很简单：当编辑器出现灰色建议时，按 Tab 接受。刚上手时，你需要刻意训练自己多看编辑器里的补全提示，也要留意底部状态栏里的 Cursor Tab 状态。很多机械重复、格式统一、局部同步的改动，不需要你手打，也不需要开 Agent，Tab 就能完成。

Tab 适合低风险、局部、连续的小改动。比如补齐类型、同步命名、生成相邻结构、扩展重复代码块。它不适合交付一个完整需求，因为它不会像 Agent 那样全局规划、读多个文件、跑验证。记住这个边界：光标附近的编辑交给 Tab，跨文件任务交给 Agent。

刚上手可以专门做三个小练习。第一个练习是在 README 里写一段列表，让 Tab 补齐下一项，感受它对格式的延续能力。第二个练习是改一个函数参数名，再观察它是否提示你同步改相邻调用。第三个练习是写一段重复结构，比如配置项、表单字段、测试用例，让它自动延续模式。练习的目的不是炫技，而是建立判断力：什么时候建议可以直接接受，什么时候应该停下来自己看。

遇到不合适的 Tab 建议，不要为了省事硬接受。继续输入几个字符，或者移动光标，让 Cursor 获得更明确的局部上下文。Tab 的质量高度依赖光标附近的代码质量，如果前后代码命名混乱、格式不统一，它也容易延续这种混乱。把文件局部整理干净，往往比反复抱怨补全不准更有效。

5. Agent入口

Cursor 官方 Quickstart 建议打开项目后，先用 Cmd+I 打开 Agent，让它解释代码库。这个动作非常适合入门，因为它不直接修改文件，却能让你看到 Agent 如何搜索仓库、读取相关文件、总结入口模块和关键目录。

可以直接使用这个 Prompt：

Explain this codebase. Point me to the main entry points, key modules, and anything I should read before making changes.

如果你希望中文输出，可以改成：

请解释这个代码库。重点说明主要入口文件、核心模块、目录结构，以及我在修改代码前应该先阅读哪些文件。先不要修改任何文件。

Agent 的能力不只是聊天。官方文档里列出的 Agent 工具包括语义搜索、文件搜索、读取文件、编辑文件、运行 shell 命令、浏览器控制等。它还能在重要修改前创建 checkpoints，也就是会话内的代码快照。如果 Agent 走偏，可以从聊天时间线里的 checkpoint 预览并恢复。这里要分清：checkpoint 适合撤销 Agent 会话内的改动，长期版本管理仍然要靠 Git。

第一次让 Agent 解释项目时，重点看它有没有说清三个信息。第一，入口在哪里，比如前端项目的 src/main.ts、app/page.tsx，后端项目的 main.go、cmd/server。第二，核心业务目录在哪里，比如 components、services、routes、internal。第三，验证命令是什么，比如测试、Lint、构建、类型检查。只要这三件事没说清，就继续追问，不要马上让它写代码。

你也可以要求 Agent 输出一份阅读顺序。对新手来说，直接看完整代码库很容易迷路；让 Agent 先列 5 个最该看的文件，再逐个解释，会比让它一口气总结全部目录更实用。这个阶段的目标是建立项目地图，不是急着得到一个漂亮回答。

6. 小改动流程

理解项目后，不要立刻交一个大需求。官方 Quickstart 也建议先做一个小而安全的改动，比如优化文案、修一个小 UI 问题、补一个边界提示。小任务能让你完整经历 Cursor 的工作闭环：提出任务、看它修改、审查 diff、运行检查、确认结果。

推荐用这样的 Prompt：

请先建议这个项目里 3 个小而安全的改进点。每个改进点说明影响范围和风险，不要直接修改代码。等我选一个后再开始。

选定一个任务后，再让 Agent 执行：

请实现第 2 个改进点。动手前先列出你准备修改的文件和原因。完成后请运行项目已有的检查命令，并输出验证结果。

这个流程故意多了一步确认。它让你在 Agent 动手前看到修改范围，避免它为了一个小问题去动一堆无关文件。入门阶段不要追求全自动，先养成看计划、看变更列表、看 diff、看验证结果的习惯。

改完后一定要审查 diff。Cursor 会显示 Agent 对文件做了什么，你可以逐处看改动是否符合预期。不要因为 AI 说完成了就直接接受。真正的完成标准是：diff 合理、运行检查通过、页面或功能表现符合需求。

审查 diff 时先看文件数量，再看每个文件的改动理由。一个很小的文案需求，如果改了 10 个文件，就应该停下来问它为什么。一个 UI 调整任务，如果顺手重写了业务逻辑，也要回退或让它收窄范围。Cursor 能做大范围修改，但入门阶段要先养成小步提交的习惯。

验证也不要只看 Agent 的总结。它说运行通过，你要看它实际跑了什么命令、命令输出是什么、有没有跳过测试。如果项目没有现成测试，就至少运行构建或类型检查；如果是页面改动，就打开页面看效果。Cursor 的价值是把改动速度提上来，不是替你取消验收。

7. Plan Mode

小改动可以直接用 Agent，大改动最好先用 Plan Mode。官方 Quickstart 里提到，Plan Mode 适合跨多个文件、需要调研、需要在编码前获得确认的任务。你可以在 Agent 输入框里按 Shift+Tab 切换 Plan Mode。

Plan Mode 不会马上写代码。它会先研究代码库，找到相关文件，必要时问澄清问题，生成详细实现计划，然后等待你批准。这个机制非常适合新手，因为你能在 AI 写代码前判断方向是否正确。方向错时，改计划比改一堆代码便宜得多。


Plan Mode 的正确用法是先改计划，不是急着点击执行。你可以要求它拆小任务、减少改动范围、补验证步骤、先做最小可用版本。等计划清楚后，再让它执行其中一个任务，而不是一次执行全部。

一个合格的 Plan 至少要包含四块内容：要改哪些文件，为什么改这些文件，每一步改什么，最后怎么验证。缺少文件范围，说明它还没有定位到实现点；缺少验证步骤，说明它只是准备写代码，没有准备交付。你可以直接这样要求它补充：

这个计划还不能执行。请补充：
1. 每个待修改文件的作用
2. 为什么必须修改它
3. 每一步完成后的验证方式
4. 哪些文件明确不应该改

Plan Mode 最适合用在影响面不清楚的任务上，比如重构登录流程、接入新接口、调整路由结构、统一错误处理。对于只改一个按钮文案、补一个 README 小节、修一个错别字的任务，直接用 Agent 或局部改动 Prompt 更快。

8. 局部改动

除了把完整任务交给 Agent，Cursor 也适合做更小范围的局部改动。做法是先把光标放到具体文件或具体小节，再在 Agent 输入框里明确约束修改范围，例如只改当前 README 的某个小节，不要改其他文件。这样既能利用 Agent 的理解能力，又能避免它把一个局部问题扩散成全项目修改。

示例 Prompt：

请只修改当前 README.md 里 Local Development 这一小节，把步骤改得更清楚，不要改其他文件。

或者：

给这个表单提交逻辑增加 loading 状态和失败提示，不要改动组件外部 API。

局部改动和完整 Agent 任务的区别在于控制粒度。你明确知道要改哪一小块，就把文件名、章节名、函数名和不允许改动的范围写清楚；你只知道需求，需要 AI 自己找相关文件，就先让 Agent 调研和列计划。这个边界能避免把简单任务做重，也能避免把复杂任务塞进一个过窄的指令里。

局部改动的 Prompt 最好包含三类限制。第一是文件限制，比如只改 README.md，不要修改其他文件。第二是行为限制，比如保持命令不变，只优化说明文字。第三是输出限制，比如改完后给出 diff 摘要，不要顺手格式化全文件。这些限制看起来啰嗦，但能显著降低无关改动。

如果你发现 Cursor 总是改多了，不一定是模型不行，很多时候是指令边界太松。把任务拆到文件、函数、小节这个级别，它会稳定很多。入门阶段宁可多写两句限制，也不要让它猜你的隐含边界。

9. 上下文引用

Cursor 对话里可以用 @ 指定上下文。对 AI 编程来说，上下文比 Prompt 文字本身更重要。你问一个函数怎么改，如果没有告诉它相关文件、依赖、接口约定，它只能猜；你用 @ 把文件、目录、文档、代码符号带进去，它的回答会稳定很多。

入门阶段先掌握三类引用就够。第一，引用文件或目录，让 Agent 看具体代码。第二，引用文档，让它基于官方资料而不是记忆回答。第三，引用 Git 或 diff，让它根据当前改动做审查。后面讲上下文与记忆时，会把 @file、@folder、@docs、@web、@git 这些系统拆开讲。

一个很实用的习惯是：每次任务开始前，先明确告诉 Cursor 看哪些文件，不要让它在整个项目里盲搜。例如让它修改登录页面时，可以先 @app/login/page.tsx、@components/auth-form.tsx、@lib/auth.ts，再描述任务。上下文越准确，改动越集中。

引用上下文时不要贪多。一次任务塞进十几个文件，并不一定更准，反而可能让 Agent 在无关信息里分心。更好的做法是先引用入口文件和直接相关文件，让它说明还需要看哪些依赖；它提出理由后，再补充相关文件。这样既能减少上下文噪音，也能让你知道它为什么需要某个文件。

引用文档时也一样。让 Cursor 直接查文档或引用官方资料，比让它凭记忆回答更稳，尤其是框架版本、API 变更、配置项名称这类容易过时的内容。工具越新，越要把上下文交给它，而不是只靠一句泛泛的需求描述。

10. 安全习惯

Cursor 能改文件、跑命令、访问浏览器，能力越强，越要建立安全习惯。入门第一天最重要的三条是：先用练习项目，复杂任务先 Plan，改完必须看 diff 和验证结果。

第二条是不要让 Agent 在不清楚边界时大范围重构。看到它准备改很多文件，先让它解释每个文件为什么要改。如果理由不清楚，就让它收窄范围。第三条是对终端命令保持审查，尤其是删除文件、安装依赖、改数据库、改环境变量、访问生产服务这类动作。

第四条是用 Git 管住长期版本。Cursor 的 checkpoints 适合会话内撤回 Agent 改动，但它不能替代 commit。每完成一个小功能并验证通过，就提交一次。这样就算后续 AI 改坏了，也能通过 Git 回到稳定状态。

正式动手前建议先看一眼工作区状态：

git status --short

如果已经有别人或自己之前留下的未提交改动，先不要让 Agent 大范围修改。最稳的做法是把当前状态提交、暂存或至少记录下来，再开始新的 AI 任务。否则 Agent 改完之后，你很难区分哪些是它刚改的，哪些是原来就存在的。

运行命令也要分级看待。读取文件、查看状态、运行测试通常风险较低；安装依赖、批量格式化、删除文件、迁移数据库、修改环境变量就要谨慎。看到高风险命令时，先让 Agent 解释目的和影响范围，再决定是否执行。

11. 入门工作流

把前面的内容串起来，Cursor 的第一天工作流可以固定成七步。第一步，安装并登录。第二步，导入 VS Code 设置。第三步，打开一个练习项目。第四步，用 Agent 解释代码库。第五步，让 Agent 建议三个小而安全的改进点。第六步，选择一个改进点执行并审查 diff。第七步，运行检查命令并提交。

这个工作流看起来很朴素，但它覆盖了 Cursor 的主干能力：迁移、读项目、提建议、改代码、看 diff、跑验证。你不需要第一天就掌握 Rules、MCP、Cloud Agent、BugBot。先把这条路径练熟，后面的高级能力才不会变成一堆按钮名。

可以把第一次任务写成这个 Prompt：

请帮我熟悉这个项目。先不要修改文件。

请完成：
1. 解释项目结构和主要入口
2. 列出我应该先阅读的 5 个文件
3. 建议 3 个低风险小改动
4. 等我选择一个改动后，再进入实现

等你选择任务后，再追加：

请实现这个小改动。动手前先列出准备修改的文件。完成后展示 diff 摘要，并运行项目已有的验证命令。

这个模板简单，但足够把 Cursor 的第一轮体验跑通。后面你可以把它扩展成更严格的团队工作流，比如必须先 Plan、必须引用规则文件、必须跑测试、必须生成 PR 描述。

12. 常见问题

12.1 迁移成本

如果你来自 VS Code，迁移成本通常很低。Cursor 可以导入扩展、主题、设置和快捷键，也可以和 VS Code 同时安装、同时打开同一个项目。需要注意的是扩展来源不同，个别扩展可能需要替代方案。

12.2 Tab边界

Tab 适合编辑器附近的小改动，不适合完整需求。它的价值是省掉连续机械修改，而不是替你做架构决策。看到灰色建议时先判断方向，对了就接受，不对就继续手写或改用 Agent。

12.3 Agent边界

Agent 适合完整任务，但不是越自动越好。复杂任务先让它 Plan，大范围改动前先看文件清单，完成后看 diff 和验证结果。不要把没有需求边界的任务直接交给它。

12.4 版本控制

Cursor checkpoints 可以撤回 Agent 会话里的改动，Git 用来做长期版本管理。两者都重要，但职责不同。正式项目里，验证通过后还是要 commit。

13. 小结

Cursor 的入门重点不是记住所有功能，而是建立正确的使用顺序。先把它当成一个熟悉的 VS Code 工作台，完成安装、登录和迁移；再用 Tab 处理光标附近的连续编辑；用局部改动 Prompt 控制小范围修改；用 Agent 读项目和完成完整任务；遇到跨文件或高风险改动，就先切到 Plan Mode。

这套节奏跑顺后，Cursor 才会从一个会聊天的编辑器，变成真正能参与开发流程的 AI 编程工具。你负责设定目标、审查计划和验收结果，它负责读代码、改文件、跑命令和给出差异。第一天只要把这条闭环练熟，后面学习 Rules、上下文、MCP、云端代理都会顺很多。
